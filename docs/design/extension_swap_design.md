# 拡張子付け替えシステム設計書

## 目的

**「途中から飽きる」の解消。**

現状、プレイヤーの強化は StageSelect でのファイル選択のみで確定し、InGame 中は変更できない
（`game_design.md` 参照）。手数も通常攻撃・ダッシュ・必殺技で固定のため、
部屋を進めるほど「自分が変化していく感覚」がなくなり作業化する。

道中に **拡張子を付け替える／スロットを増やす** 選択を挟むことで、
ビルドを組み立てる感覚を生み、周回のたびに異なる展開になるようにする。

### なぜ「拡張子」なのか

このゲームの本体は **ユーザー自身の Windows で戦うこと**。
道中報酬に汎用的な強化アイテムを置くと語彙だけが Windows 風になり、本体から離れる。
既に成立している拡張子スロットをそのまま道中に持ち込むのが、
世界観・既存実装・リプレイ性のすべてに対して素直。

---

## ゲームループ

```
ブロック破壊／敵撃破
  → 拡張子の欠片（実PC由来）
  → リネーム端末(F2)で付け替え → 左下ステータスで差分を確認
レアブロック
  → メモリモジュール → スロット枠が増える → さらに積める
```

## 1. リネーム端末（拡張子付け替え）

### 操作

| 項目 | 内容 |
|---|---|
| 設置 | 各部屋に配置するオブジェクト。戦闘終了後に使用可能 |
| 接近時 | 足元に小さく `F2 : 名前の変更` と表示（Windows風の淡いツールチップ） |
| 決定キー | **F2**（Windows のリネームショートカット。説明不要で伝わる） |
| 開いた状態 | `PauseManager` で時間停止 |

Windows で拡張子を変える操作＝リネーム。ここを踏襲することで、
対象読者（エンジニア・面接官）に対して操作説明なしで意図が伝わる。

> **注意**: `F2` は現状 DEBUG のシーンビューに割り当てられている（`PauseManager` 周り）。
> 実装前に衝突を確認すること。

### 画面構成

StageSelect の「ファイル選択ウィンドウ」＋「パラメータウィンドウ」と
**同じレイアウト・同じ配色（Windows 11 / Fluent）** の2パネルを InGame 内に開く。
「あのときの選択画面がゲーム内に呼び出された」という見せ方にする。

```
┌─ ファイルスロット ─┐  ┌─ パラメータ ─┐
│ [1] report.txt     │  │ HP   120 → 140 │  ← 差分を緑/赤で表示
│ [2] tool.exe       │  │ ATK   42 →  52 │
│ [3] （空き）       │  │ DEF   18       │
│   [ 参照... ]      │  │ ...            │
└────────────────────┘  └────────────────┘
```

### ファイル選択の方法

**エクスプローラーからの選択を維持する。**
「参照...」を押した瞬間だけ `GetOpenFileNameA` を直接呼ぶ。

`GetOpenFileNameW` は使わない（comdlg32.dll 内部で `__debugbreak()` が走る）。
既存の `FileSelectWindow::toUtf8` と同じ変換経路を通す。
→ 詳細は memory `select-window-debugging` を参照。

## 2. アーキテクチャ方針：WebView は再利用しない

### 結論

| 再利用する | 再利用しない |
|---|---|
| レイアウト・配色・寸法 | Win32 / WebView のウィンドウ実装 |
| ボーナス計算ロジック | `Win32SelectWindowManager` の管理構造 |
| `GetOpenFileNameA` 呼び出し部 | |

見た目は `IUIRenderer` を使って **DxLib 側で描き直す**。
`EquipmentSlotView` が既に Fluent 準拠のスロット（角丸4px）を描いているため、それを拡張する。

### WebView をそのまま持ち込まない理由

- **フォーカスが DxLib から奪われる**。全画面ではデバイスロストや復帰時の描画崩れの温床
- メッセージポンプが二重になる（`pumpMessages()` を InGame ループから回す必要が出る）
- WebView の初期化コストが乗る。端末に触るたびに数百ms〜秒の間が入るとテンポが死ぬ
- メモリ。3.5GB → 1.3GB まで削った経緯に逆行する（memory `memory-optimization`）
- セレクト画面が常時最前面のせいで F4 退避を足した問題が、
  今度は「ゲーム画面が隠れる」形で再発する

技術的に不可能ではなく、**得られるもの（見た目の一致）に対してコストが大きすぎる**という判断。

## 3. 共通化すべきもの（ズレると破綻する順）

### 3-1. ボーナス計算の一本化 【最優先】

現在、拡張子ボーナスの合算は3箇所に散っている。

| 場所 | 用途 |
|---|---|
| `Win32SelectWindowManager.cpp:308` | パラメータウィンドウ表示用 |
| `FileSelectWindow.cpp:306,324` | スロット内のボーナス表示用 |
| `InGame.cpp:380-387` | 実際のプレイヤーへの適用 |

これを **純粋な計算関数** として game 層に切り出し、全経路がここを通るようにする。

```cpp
// game/utility/ExtensionBonusCalculator.h（案）
[[nodiscard]] core::data::FileExtensionBonus calcTotalBonus(
    const data::FileEquipmentData& equipment,
    const core::iface::IResourceManager& resourceManager) noexcept;
```

二重実装のままだと「セレクトでは +10 と出たのに実際は +8」の不整合が必ず出る。
InGame で付け替えられるようになると、表示と実効値のズレは即座にバグとして露見する。

### 3-2. `PlayerData` への適用を「再計算可能」にする 【必須】

現在の `PlayerData::applyExtensionBonus()`（`PlayerData.h:237`）は
`m_attackPower += bonus.atk;` のように **既存値へ加算するだけ**で、元に戻せない。
付け替えのたびに呼ぶと二重加算になる。

対応：**基礎値を保持し、`基礎値 + 合算ボーナス` で毎回再計算する形に変える。**

```cpp
// 案：適用ではなく再構築
void rebuildWithBonus(const core::data::FileExtensionBonus& total);
```

留意点：

- `m_maxHp` が下がったとき、現在HPが上限を超えないようクランプする
- 現在HPは維持する（付け替えで全回復してしまうと回復手段として悪用される）
- `m_criticalRate` の 1.0 頭打ちは合算後に一度だけ適用する
- `m_projectileSpeedBonus` / `m_projectileRangeBonus` は加算ぶんのみ保持なので、
  そのまま合算値で上書きすればよい

### 3-3. スロットの真実の置き場を一元化

現在 `Win32SelectWindowManager` が `m_slotPaths` / `m_slotExtTypes` を自前で持ち、
`FileEquipmentData` にも同じものがある **二重管理**。
InGame でも書き換わるようになると破綻する。

→ **`FileEquipmentData` を唯一の持ち主**（所有は `GameManager`）とし、
セレクト画面側はそれを参照するだけにする。

### 3-4. `FileEquipmentData` の拡張

| 変更 | 理由 |
|---|---|
| 拡張子だけを差し替える経路を追加 | 現状 `setFilePath()` はパス→拡張子の一方通行 |
| `MAX_SLOTS` を「現在値 + 上限」に分離 | スロット枠の拡張に対応するため |
| 保持内容をパスから「表示名 + 拡張子種別」へ寄せる | 付け替えでパスと拡張子が食い違うため |

### 3-5. レイアウト定数の共有

スロットの寸法・配色・角丸半径を1箇所に置き、
WebView 側の CSS と DxLib 側の描画が同じ数値を見るようにする。
完全一致は無理でも、印象を揃えるには十分。

## 4. 拡張子の入手経路

### 方針：InGame 中に実PCを走査しない

Loading 時に、選択したフォルダを走査して **実在した拡張子のヒストグラム**を作り、
それをダンジョンのドロップテーブルにする。
難易度決定で既にフォルダを舐めているため、そのついでに集計するだけで済む。

| 選んだフォルダの中身 | ドロップ |
|---|---|
| `.png` が大量にある | `.png` の欠片が高頻度で落ちる |
| `.exe` が数個だけ | レアドロップになる |
| 一度も存在しない拡張子 | そのプレイでは手に入らない |

これにより：

- 「自分の Windows で戦っている」がプレイ中ずっと維持される
- **フォルダを変えるとドロップ内容が変わる＝リプレイ性**が自動的に生まれる
- InGame 中にファイルダイアログを開かずに済む（テンポ・安定性）

「参照...」による直接選択と、ドロップした欠片からの選択は併存させる。

## 5. スロット枠の拡張

| 項目 | 内容 |
|---|---|
| アイテム名 | メモリモジュール（RAM） |
| 効果 | 装備スロットを1つ増やす |
| 範囲 | 3 → 5 で打ち止め |
| 入手 | レアブロック（`system32` 的な色違い）の破壊 |

「積めるものが増える＝メモリが増える」で理屈が合う。

**渋く配ること。** 枠が余っていると「拾って挿すだけ」の作業になる。
枠が埋まった状態で「何を捨てて何を挿すか」を迫る時間を長く保つのが設計の肝。

`EquipmentSlotView` は現在 `SLOT_COUNT{ FileEquipmentData::MAX_SLOTS }`（`.cpp:206`）の
固定前提でレイアウトしているため、可変枠に対応させる必要がある。

## 6. 破壊可能ブロック

破壊対象は **圧縮ファイル（.zip の塊）**。破壊＝解凍で理屈が通る。

| 種類 | 内容 |
|---|---|
| 通常ブロック | 拡張子の欠片が出る |
| レアブロック | メモリモジュール（枠拡張）が出る |
| `malware` ブロック | 壊すと敵が湧く。リスクリターンの選択になる |

ブロック破壊は**単体では飽きを解消しない**。上記のゲームループに接続して初めて機能する。

## 7. 左下ステータス表示

現在 HP のみ表示している左下 HUD に、拡張子ボーナスが乗る全項目を出す。

| 項目 | 備考 |
|---|---|
| HP / ATK / DEF / SPD | 常時表示 |
| 攻撃射程 / クリティカル率 | 常時表示は圧迫するため Tab 長押しで展開 |
| 弾速 / 飛距離 | Window弾を使う構成でのみ表示 |

`FileExtensionBonus` のメンバに素直に対応させる。

**数字を並べるだけでは意味がない。**
リネーム端末を開いている間だけ、差し替え後の差分を `ATK 42 → 52` のように
緑/赤で見せること。これがないと選択が博打になり、悩ませる設計が機能しない。

見た目は**タスクマネージャのパフォーマンスタブ**に寄せると、
右下の装備スロット（Fluent コントロール）と喧嘩せず統一感が出る。

## 実装順

飽きの主因は「道中で自分が変化しないこと」なので、まず 1〜3 だけで検証する。
4 以降は成立を確認してから足す。

| # | 内容 | 分類 |

| 5 | リネーム端末オブジェクトと接近時のツールチップ | feat |
